> **TL;DR:** We asked frontier agents to design a library, then judged it only by how well _other_ agents could build with it. Two (Opus 5.5 and Fable 5.1) beat the human-written library. One (DeepSeek V4 Pro) is worse than no library at all. And on 11 of 15 tasks, they just copy the human design.

We are fast approaching an inflection point where agents will work more with code designed by other agents than by a human engineer. Existing benchmarks don't adequately measure this because they focus on the _library's_ correctness rather than its utility to future users. That is why I am excited to release [LibraryDesignBench](https://ldbench.com), a two-phase benchmark that evaluates an agent-written library's quality only through how _downstream agents use it_. LDB tasks an agent with designing a library from only a feature list and two descriptions of how it will be used. We then task three different, less capable, agents with leveraging the library to write correct but simple programs.

At no point do we prescribe signatures their library must expose. Nor do we ever guide them to specific abstractions or patterns they should use. We intentionally give them underspecified, vague, and ambiguous library specifications because frontier agents need to envision how future agents will use their library, what they will need, and what design will work best. LibraryDesignBench gives agents this vast freedom because the evaluation needs to serve as a test bed for understanding what patterns _agents_ actually prefer, not what we think they will prefer.

## Evaluating A Library Without Inspecting It

A library that implements something correctly does not immediately provide any value – it needs to be correct _and_ make future code simpler. Thus, the _only_ way to measure a library's quality is to observe how much future users benefit from its design decisions. LibraryDesignBench does this in two phases:

1. **Design Phase:** The agent implements a full library from an intentionally non-prescriptive specification.
2. **Evaluation Phase:** We evaluate the library by observing multiple different implementer agents attempt to solve problems using it.

The only aspect we check in the design phase is if the library is installable in their internet-restricted environment, as we pre-install all libraries for evaluation since trying to install a library is not part of the signal we care about. We then task three agents (5.6 Luna on Codex, DeepSeek v4.1 Flash on mini-SWE-agent, and GLM 5.3 Flash on mini-SWE-agent) with solving programming problems with the library in as little code as possible. Each problem $\times$ agent $\times$ library is run in its own environment without internet access, with high reasoning, and with the library pre-installed. We use a [highly prescriptive prompt](https://github.com/SprocketLab/librarydesignbench/blob/dev/configs/prompts/library_use_inst.md) to ensure agents attempt to fully exploit the library.

We now take these solutions and score each with:

$$
\text{score} = \text{pass rate}(y)^2 \cdot \text{simplicity}(y)
$$

Pass rate is the percentage of tests passed, and we square it to penalize incorrectness more harshly than simplicity. Simplicity is defined as:

$$
\text{simplicity}(y) = \frac{1}{|\mathcal{M}|} \sum_{m \in \mathcal{M}} \min\left\{\frac{m(y^*)}{m(y)},\, 1\right\}
$$

$\mathcal{M}$ is the set of static metrics we use to compare how far off the solution written with the library is from the golden reference, $y^*$, written with the real production library. The metrics we use are: Source Lines of Code, Cyclomatic Complexity, Cognitive Complexity, and Halstead Volume. You can read more details about our scoring methodology and standard error definitions in section 2 of the paper.

## Agents Copy Human Designs But Worse

We evaluate our 15 library design tasks on 9 frontier models across 11 setups, all using high reasoning. We run each task three times per setup, for a total of 45 libraries. We then run each implementer agent once per generated library across our 242 problems, for a total of 2,178 trials per setup. We also evaluate setups with no library present (given a different prompt) and the case where they have pre-installed the human-designed production library. For these two setups, the evaluation agents are run for the same set of 2,178 trials.

We find that both Opus 5.5 and Fable 5.1 can outperform the production libraries, while only DeepSeek V4 Pro designs a library that actively hurts the agents. For both Astra & Fable, mini-SWE-agent outperforms their native harnesses. In the case of Claude Code, Fable's library lacked documentation compared with the library written in mini-SWE-agent.

<LdbConvergence />

Beyond harness peculiarities, the biggest trend we observed is that on 11/15 tasks, agents copied a design pattern from the corresponding production library. Surprisingly, these patterns are the exact ones the implementer agents used when given the production library. Our failure analysis indicates that the implementer agents end up writing more complex code than is needed because interfaces are either too rigid to use or require verbose code. In the former case, agents reimplement functionality the libraries provide, adding bugs in the process.

## Can Agents Use Libraries Without Instruction?

Our main evaluation prompt is rather heavy-handed because we need agents to fully exploit the library to measure its upper bound. But we also want to understand how _models_ will behave given [minimal additional instructions](https://github.com/SprocketLab/librarydesignbench/blob/dev/configs/prompts/minimal.md). Thus, we also release **LibraryUseBench**, our evaluation phase in which agents must use the production library to write as little code as possible. All agents use mini-SWE-agent and use High thinking. Opus 5.5, unsurprisingly, is the best model evaluated, while 5.6 Luna rounds out the lower end.

## Do Agents Prefer Non-Human Design Patterns?

We conclude with an exploratory prompting intervention in which we explicitly guide the agent based on the trends we observed, instruct it to use subagents to test its design, and ask it to use as concise symbol names as possible. We find this provides a modest benefit for downstream agents, suggesting that the design patterns we prefer are unlikely to be the ones agents prefer.
