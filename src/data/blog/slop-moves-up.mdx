> **TL;DR:** Agent's can now solve significantly more SlopCodeBench checkpoints while writing significantly less slop. The slop, however, has not been eliminated. Rather it has moved up in the stack to now infest design decisions. Our new LibraryDesignBench and LibraryUseBench show that frontier agents lack foresight to how their code will be used through both poor abstraction design _and_ complete disregard for reusing library provided code.

The amazing [Dex Horthy](https://x.com/dexhorthy) at HumanLayer has been running SlopCodeBench with every new frontier model release. His [Part I](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/benchmarking-new-models-on-slop-code-bench.md) covers pass rates, cost, and how much slop each model writes ([X post](https://x.com/dexhorthy/status/2115115507183685850)). This post is the second part follow up where we dive deeper into the actual behavioral patterns we observed.

When we began work on [SlopCodeBench](https://www.scbench.ai) a little over one year ago, there was a lot of discussion about "[slop coding](https://x.com/nearcyan/status/1902539629313847637)", [quality issues with vibe coding](https://x.com/rauchg/status/1979590878416257216), or just the general [low-quality code that came from agents](https://x.com/jsharkey/status/1968471631111614574) at the time. A bit more than a year later, we wanted to revisit to see how the field has progressed. Lets first describe what the core benchmarks in this analysis:

- **[SlopCodeBench (SCB)](https://www.scbench.ai)** tests how agents handle changing requirements. Each problem is a sequence of checkpoints. The agent writes a program for the first spec, then extends its own code for every new one. We grade it on hidden tests and on how much slop builds up in the code. There are 36 problems and 196 checkpoints, all in Python.

- **[LibraryDesignBench (LDB)](https://ldbench.com)** sees how well agents can design a library. The agent under evaluation writes the library then we score it only on how a much code is reduced when a fixed set of implementor agents use it to solve problems. More in the [launch post](/posts/library-design-bench/).

- **[LibraryUseBench (LUB)](https://ldbench.com/usage)** tests agents with solving a programming problem using a human written library with minimal instruction. These are the _exact same_ problems we use in LDB's implementor phase but without the highly prescriptive prompt.

## The Good

### Solve rates keep climbing

Unsurprisingly, solve rates on SCB keep climbing. The strict solve rate, solution must pass _every_ test for the current checkpoint and all prior, now peaks at 16.3%, set by GPT-6 Astra XHigh (32 of 196 checkpoints). Every frontier model released since July clears 65% on core tests. The trend puts strict pass rate increasing by 0.9 points a month, isolated by 1.5 and core by 2.3.

There have been massive reductions in the amount of lines with slop rule violations in newer models. Erosion has trended the same with some slightly regressions as well.

### Some slop just moved

Some of the anti-patterns we check for appear to have been fixed, but on closer inspection agents now work around them with minor patches:

- Silent `except Exception:` handlers became `except OSError: return None`.
- The type-check helpers our rules flag became inline `if not isinstance(...): raise` ladders.

## The Ugly

### Agents skip what the library already does

{/* NEW: the rewrite inventory over LibraryUseBench and LDB solutions (O_rewrite). */}

The newest form of slop that is particularly concerning is the increasing scenario where an agent searches a library and finds the functionality its needs, then decides it was actually better all along to just implement it itself. Besides being infuriating, this is easily one of the biggest behaviors that just needs to change.

<SlopRewrite />

On LibraryUseBench, every model hand-writes something the library already does, in 73% to 100% of its solutions. Even the best ones do it in nearly 3 of 4 solutions written. It will become ever more important to solve this as agents increasingly work with agent written code over human written code.

LibraryDesignBench measures exactly this and highlights that, while agents do still write redundant functionality, it occurs in only 40% of their solutions. This is not, unfortunately, because agents somehow mastered software design for other agents. It is because for LDB, we have to use an incredibly prescriptive prompt. The same prompt with human designed libraries leads to ~17% reimplimentation rate.

## What Now?

I might be biased, but clearly every new model that comes out should put SCB, LDB, and LUB on their model cards. And hire me after I defend in the spring.

Beyond these three benchmarks? We need longer horizon benchmarks, benchmarks where agents have to interact with each other, and benchmarks where agents need to consider how their decisions will impact future agents. Because agents will increasing use artifacts designed by other agents and not humans.
