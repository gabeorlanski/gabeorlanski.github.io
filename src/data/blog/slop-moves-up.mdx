**TL;DR**

When we began work on [SlopCodeBench](https://www.scbench.ai) a little over one year ago, there was a lot of discussion about "[slop coding](https://x.com/nearcyan/status/1902539629313847637)", [quality issues with vibe coding](https://x.com/rauchg/status/1979590878416257216), or just the general [low-quality code that came from agents](https://x.com/jsharkey/status/1968471631111614574) at the time. Today, we'll look at what's gotten better and what's gotten worse since we released SCB.

This would not have been possible without the amazing [Dex Horthy](https://x.com/dexhorthy) at HumanLayer for running every new model with SlopCodeBench. His [Part I](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/benchmarking-new-models-on-slop-code-bench.md) covers pass rates, cost, and how much slop each model writes ([announcement on X](https://x.com/dexhorthy/status/2115115507183685850)).

{/* NEW */}
We compare five older runs (Opus 4.6, Opus 4.7, GPT-5.4, GPT-5.5, GLM 5.1) to ten newer ones (Opus 5.5, Fable 5.1, the GPT-6 family, GPT-5.6 SOL and GLM 5.3). Every code measure uses the final snapshot of each problem and excludes tests.

### The Good

Unsurprisingly, solve rates on SCB keep climbing. The strict solve rate, the share of checkpoints where every test passes, now peaks at 16.3%, set by GPT-6 Astra XHigh (32 of 196 checkpoints). Every frontier model released since July clears 65% on core tests.

<SlopTimeline keys={["strict", "isolated", "core"]} client:visible />

{/* NEW */}
And it is not a fluke. Across every setup, all three solve rates trend up: strict by 0.9 points a month, isolated by 1.5 and core by 2.3.

None of these are bad lines of code. They are bad design decisions: what a handler catches, where validation lives, what a function is responsible for. No line-level rule will ever flag them. And every agent that builds on this code inherits them.

One regression costs real tests. All six new GPT runs write timestamps with microseconds, even though every example in the spec has whole seconds. At checkpoint 2 they pass 1 of 12 core tests, where GPT-5.4 and GPT-5.5 passed 10 of 12. The failure starts at checkpoint 1, and none of the six ever fixes it.

<ExBad6 />

The GPT-6 models also grow the functions they already have. Between 22% and 29% of the code they add at each checkpoint lands inside an existing function; GPT-5.4 and GPT-5.5 were at 15% and 17%. GPT-6 SOL Medium's `grade()` goes from complexity 22 to 192 over seven checkpoints, gaining an optional parameter at each step. By checkpoint 7, one flag changes what the function returns.

What is more concerning, in my opinion, is that the Claude models and GLM 5.3 have started writing Python 2 idioms into a Python 3.12 codebase: `%` formatting, `class X(object)` and `Base.__init__(self, ...)`. `%` formatting is the main style in 14–23 of 36 problems for Opus 5.5, Fable and GLM 5.3, against at most 3 for any older run. Each problem's style is set at checkpoint 1 and almost never changes.

SlopCodeBench only looks at Python. LibraryDesignBench covers Python, Rust, TypeScript and Haskell, so we counted the same four kinds of smells in every library and compared them to the human-written libraries for the same task:

The good news holds in every language. In Rust, TypeScript and Haskell, agent-written libraries have fewer crash shortcuts, suppressions and type-system escapes than the human ones. The bad news is error handling, and it looks different in every language. Python libraries silence broad exceptions 3x as often as humans do. Haskell libraries catch `SomeException`, which the human libraries never do. TypeScript libraries assert non-null where DOMPurify never does (only one task, so take that one lightly).

### The Ugly

All of these pale in comparison to the largest issue we observe in the newest models: they would rather write a library than use one.

The most common form is a hand-written fallback. The agent lists a library in `requirements.txt`, guards the import, and writes its own copy for when the import fails. The benchmark always installs the requirements, so the copy never runs. The five older runs did this in 4 problems (156 lines). The new runs do it in 31 problems (9,060 lines), all from Opus 5.5, Fable 5.1 or GLM 5.3. Opus 5.5 XHigh's `xjq` declares `lxml` and carries a 1,058-line XPath engine behind it, extended at every checkpoint. In Fable's logs, 10 of 14 fallbacks were written without any import ever failing.

Sometimes there is no dependency at all. On `file_query_tool`, Opus 4.7 built on `duckdb` in 324 lines; Opus 5.5 XHigh wrote its own SQL engine in 3,375. Here the extra code passed more tests.

This matters more now that agents write code for other agents. [LibraryDesignBench](/posts/library-design-bench/) measures exactly that: one agent designs a library, and other agents build on it. The best agent-designed libraries now score above the human ones: Opus 5.5 scores 48.9 and Fable 47.5, against 46.6 for the production library and 34.4 with no library at all.

The failures are mostly about reuse. In 2 of 3 failed tests the library could already do the job:

- In 43%, the implementer didn't find the capability, or missed part of how to use it.
- In 25%, it found the capability and wrote its own version anyway, because of how the library was designed.

<SlopReuse client:visible />

To be fair to the agents, the code implementers write on top of the best agent libraries is as clean as on the human one. Erosion in their programs is 0.395 on Opus 5.5's library, 0.396 on Fable's and 0.400 on the human library, against 0.781 with no library at all. The problem is not that the libraries produce sloppy programs. It is that implementers routinely skip or rewrite what the libraries already provide.

The same models that re-implement the most in SCB copy the most from human libraries in LDB. Opus 5.5's and Fable's libraries reuse about 30% of the production library's public names, against 13% for GPT-6 SOL. They copy the interface and write their own implementation behind it.

Some code is aimed at other agents outright:

```python showLineNumbers=false
BeautifulSoup = UglyPie  # familiar alias for agents trained on bs4
```

Line by line, the code is cleaner. Above the line, the slop is moving into designs, and that is where it compounds.

This is why we need both benchmarks. SlopCodeBench needs a new version that grades design, not just lines. Does the agent use the library it declared? What do its error handlers catch? Does the structure hold up as the spec changes? And it needs to do this in more than Python. Code written for other agents also needs to be judged by those agents. That is exactly what LibraryDesignBench does.
